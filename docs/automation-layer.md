# v2 automation layer

`data/v1/` is the **evidence layer**: what we know about each broker and how we know it. Nothing there is executable.
`data/v2/` is the **automation layer**: how a worker searches a broker for one consenting person, files a removal through the most legitimate channel, and checks the result. It joins v1 by `id`.

| Path | Role |
| --- | --- |
| `data/schema/broker-automation.schema.json` | JSON Schema (draft 2020-12), `schema_version` `2.0.0` |
| `data/v2/brokers/<id>.yaml` | One hand-reviewed spec per broker or broker family. File name equals `id`. |
| `data/v2/brokers.json` | Compiled array (generated by `scripts/build_v2.py`) |
| `data/v2/brokers.csv` | Flat view, one row per spec, column order in `scripts/v2_common.py` (`CSV_COLUMNS`) |
| `docs/examples/spokeo.yaml` | Worked example that passes the schema |

```
pip install -r requirements.txt
python scripts/validate_v2.py   # schema + cross-file rules
python scripts/build_v2.py      # writes brokers.json and brokers.csv
```

## Rules

- Unknown is `null`, never `false`. `false` is an observed fact.
- No personal data in this repo. Observed turnaround and relist rates are aggregates only (`observed_sample_size` of 10 or more). End-to-end evidence links point to a private store.
- Search specs are discovered with an obviously synthetic test identity, never by looking up a real person.
- Every value copied or inferred gets a `provenance` entry keyed by JSON Pointer (`/search/url_template`) with `checked_at`, `source` and `evidence_url`. That gives each field its own last-verified date.
- `source: inferred` blocks `lifecycle.status` from moving to `e2e_tested` or `live`.
- `egress.proxy_policy` is always `never_residential`, and `rate_policy.honor_retry_after` is always `true`.
- CAPTCHAs are never solved by automation. A channel that needs one gets a `human_task` step (`human_task_kind: captcha`) or a lower-ranked email/letter channel is used instead.
- If `tos.automation_prohibited` is `true`, `tos.policy_decision` must be `email_or_letter_only` or `user_assisted_only`.

## Cross-file checks in `validate_v2.py`

1. `id`, `family_id` and every `covers_ids` entry exist in `data/v1/catalog-ids.csv`.
2. `covers_ids` needs `coverage_evidence_url`; a brand is covered by at most one spec and never also has its own spec.
3. The ToS rule above.
4. `e2e_tested` / `live` need `adapter.last_e2e_result: pass` within 90 days.
5. No `inferred` provenance on `e2e_tested` / `live` specs.
6. Every `{placeholder}` in `search.url_template` is listed in `search.inputs`.
7. `removal.channels[].rank` values are unique; provenance pointers resolve.

## Canonical fields

`full_name, first_name, middle_name, last_name, name_aliases, city, region, postal_code, country, street_address, past_cities, age, age_range, birth_year, birth_date, phone, email, relatives, profile_url, record_id, signature, id_document, reason_free_text`

`scripts/v2_common.py` maps v1's raw `required_fields` strings (for example `"firstName firstName e.g. John text"`) to these names and parses `documented_processing_time` sentences into an upper bound in days (business days × 1.4, rounded up).

## Lifecycle

`draft → researching → adapter_dev → e2e_tested → live`, with `paused` (layout changed or blocked), `deprecated` and `defunct`.

## Export for apps (`data/v2/frame-export.json`)

`python scripts/build_frame_export.py` joins everything into one artifact an app can import without reading the rest of the repo:

- `brokers[]`: one object per active catalog row (same ids as `data/v1/catalog-ids.csv`), with the opt-out and request URLs, liveness verdict, family (parent company, shared portal, which spec covers it), priority, a `removal` block (primary flow `portal | form | email | letter | phone | drop | manual`, privacy email and where it came from, required canonical fields, verification steps, documented processing days, the broker's own registry-reported median, re-check and relist intervals), a `search` block, a `jurisdiction` block (coverage, statutory bases, CPPA registration, DROP) and an `automation` block (v1 class, research status, spec lifecycle, bot wall, ToS decision, `adapter_ready`).
- `archived[]`: rows removed from the catalog, with reason and evidence (`docs/liveness.md`).
- `template_by_residency` and `templates`: which request template to use for a person's residency (`US-CA`, other US privacy-law states, `CA`, `CA-QC`, `EU`, `GB`, `ANY`). Bodies are in `data/v2/templates.json` and `templates/*.md`.
- `meta`: export version, counts and a SHA-256 of the broker array so importers can skip unchanged builds.

`data/v2/frame-export.ndjson` has the same broker objects, one per line. Precedence for every field is v2 spec > v1 evidence > CPPA registry > page fill, and anything that didn't come from v1 has a `provenance` entry with its URL, date and confidence. `data/schema/frame-export.schema.json` describes the format; `python scripts/validate_export.py` checks it against the schema and the catalog (same ids and count, unique domains, nothing archived still active, templates exist).

`python scripts/enrich_v2.py` copies CPPA registrations, statutory legal bases, known privacy emails (as a ranked email channel with the right template) and extracted processing times into the v2 specs, filling only empty values.

## CI

The maintainer token on the automation box can't write workflow files. Add this as `.github/workflows/validate.yml` in the GitHub web UI:

```yaml
name: validate
on:
  push:
  pull_request:
  schedule:
    - cron: "17 9 * * 1"   # Mondays: liveness pass (results are uploaded, nothing is committed)
jobs:
  validate:
    if: github.event_name != 'schedule'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: python scripts/validate_dataset.py
      - run: python scripts/validate_v2.py
      - run: python scripts/build_v2.py && git diff --exit-code data/v2/brokers.json data/v2/brokers.csv
      - run: python scripts/validate_export.py
  liveness:
    if: github.event_name == 'schedule'
    runs-on: ubuntu-latest
    timeout-minutes: 120
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: cd scripts && python liveness_check.py --pass-label "$(date +%F)-a"
      - run: sleep 3000
      - run: cd scripts && python liveness_check.py --pass-label "$(date +%F)-b" && python classify_liveness.py && python archive_entries.py --dry-run | tee ../liveness-plan.txt
      - uses: actions/upload-artifact@v4
        with:
          name: liveness
          path: |
            research/evidence/liveness-report.json
            liveness-plan.txt
```

## Priority and bootstrapping

- `data/v2/priority-impact.csv` holds the reviewed impact score (0–50) and rationale for each broker on the work list.
- `python scripts/priority.py` adds readiness from v1 and writes `data/v2/priority.csv` (`score = min(100, impact + readiness)`, tiers `launch` / `next` / `research`). Rules are in the script's docstring.
- `python scripts/bootstrap_v2.py` creates a starter spec for each id in `priority.csv`, copying only what v1 established (channels, CAPTCHA and email-verification requirements, mapped form fields, parsed processing days, legal bases from coverage, bot walls, PeopleConnect family coverage), each with provenance. It never overwrites an existing file unless `--force` is given.
- Bootstrapped search methods are marked `source: inferred` until a browser pass with a synthetic identity confirms the template.
